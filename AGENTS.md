# AGENTS.md

This file provides guidance to AI coding agents working with code in this repository.

## Commands

Development uses a virtual environment in `.venv` (pyright is configured to use it). Install with `pip install -e .[dev]`.

- Lint and format: `pre-commit run --all-files`
- Type check: `pyright`
- Run the tests (require gcc): `pytest`
- Run a comparison with PLECS (requires PLECS Standalone with the RPC interface on port 1080): `python examples/ipmsm_2kw_fvc.py`
- Run a comparison with Simulink (requires MATLAB with a MinGW-w64, gcc, or clang compiler for `mex` and the MATLAB Engine API for Python matching the MATLAB release): `python examples/ipmsm_2kw_fvc_simulink.py`; with MATLAB Function blocks (no compiler needed): `python examples/ipmsm_2kw_fvc_simulink.py --matlab`
- Run the tests of the MATLAB Function blocks in Simulink (requires the MATLAB Engine API for Python, skipped otherwise): `pytest tests/test_matlab_function.py`
- Run a native simulation and compare it with *motulator*: `python examples/pmsyrm_6kw_gn_fvc_native.py --compare`

## Architecture

- `motulator_export/plecs/sm.py`, `im.py`, and `grid.py` write PLECS models of synchronous machine drives, induction machine drives, and grid converter systems. Each provides `write_model` and `simulate`, and `export_values` gets the parameters of the control system in the *motulator* API. The shared building blocks are in `_schematic.py` (the PLECS file format: the schematic writer `_Schematic`, probes, scopes, masks, and C-Script parameters), `_common.py` (the step signals, the control-system block `ControlBlock`, the converter, the DC bus, and the model file), `_drive.py` (the mechanics, the speed controller values, and the scope), and `_rpc.py` (the simulation via the RPC interface). The package `motulator_export` exports `StepSignal` and `sampled_step`, which both exports use.
- In the control systems, each class of *motulator* is a block with a mask of the arguments of its class, in the hierarchy of *motulator*. They are described as netlists (`plecs/_netlist.py`: C blocks, selectors, multiplexers, tags, and subsystems with their connections, masks, and layout hints) in `plecs/_sm_control.py`, `_im_control.py`, `_im_vhz_control.py`, and `_grid_control.py`, with the common classes (`PWM`, `SpeedController`, `SpeedObserver`, `CurrentLimiter`, `RateLimiter`) and the top levels (`VectorControlSystem`, `VHzControlSystem`, `GridConverterControlSystem`) in `plecs/_control.py`. The masks of the composite classes compute the arguments of the blocks inside them in their initialization (MATLAB syntax, also run by PLECS), as the constructors of *motulator* do, and the masks of the top-level classes refer to the structs (e.g., `par`, `cfg`, `speed_ctrl`, and `pwm`) of the model initialization (`init_script` of the control modules: the initialization commands of PLECS, and `init_<model>.m` of Simulink, run by the model after loading and at the start of each simulation). The C blocks initialize their states from their own parameters (copying the parameters used later, since the parameters are read only in the start function), and the signal vectors (meas, fbk, ref) are defined in the C headers of the control methods (`Signals` in `_control.py`). The first input of the control system is `enable`, the gate enable of *motulator* (`ControlSystem.set_enable`, `gate_enable` in `_common.py`): while it is zero, the control system runs in standby as in *motulator* (the blocks `compute_standby_output` of the controllers, the measured converter voltage `meas.u_c_ab` as the realized voltage of the PWM, and the speed controller not updated), and the PLECS model blocks the gates of the IGBT converter (the input sampled by a zero-order hold, multiplying the gate signals); only the blocks whose operation depends on it have the input `enable`. The layout engine of `_netlist.py` places the blocks and routes the wires for both tools (`PLECS` and `SIMULINK` geometries), and `problems` checks for crossings; use `_netlist.preview` to draw a layout when changing the hints. `plecs/_render.py` renders a netlist in PLECS and `simulink/_render.py` with `+blocks/add_netlist.m` in Simulink.
- `motulator_export/c/` is the C port of the *motulator* control algorithms, run in the C-Script blocks of PLECS and the S-functions of Simulink. It follows the Python code of *motulator* closely, including the order of the state updates, and the tests in `tests/` compare it with *motulator* step by step (the C test APIs are compiled with the helpers in `tests/c_port.py`). A change in the control algorithms of *motulator* must be mirrored here. The tests pass NaN for the optional parameters so that the default values are resolved in C, as in *motulator*. The whole-system functions (e.g., `vector_control_system_compute_output`) are used by the monolithic reference control systems of the tests.
- `motulator_export/native/` simulates a *motulator* system natively: `Simulation` (`_simulation.py`) has the interface and the results of the simulation of *motulator*, and the module of the system type (`sm.py`, a subclass of `NativeSystem` in `_system.py`) checks the system and sets the parameters of its library (`c/native_sm.c`, compiled at the first use by `_build.py` and cached in the temporary directory) from the *motulator* objects. The library combines the C port of the control system, the C model of the system (`c/drive.c`), and the simulation core (`c/sim.c`: a port of the simulation loop of *motulator* with the computational delay, the PWM models, and the RK45 solver of scipy, taking the same steps). It logs the solution points and the signal groups of the control system (described by a string of their fields, e.g., `FVC_FIELDS`), which `_simulation.py` stores into the time series of the *motulator* objects, so that *motulator* post-processes the results. `tests/test_sim.py` compares the solver with scipy and the PWM models with *motulator*, and `tests/test_native.py` compares closed-loop simulations with *motulator*. A change in the simulation loop, the PWM models, or the drive models of *motulator* must be mirrored in `c/sim.c` and `c/drive.c`.
- `motulator_export/matlab/` is the MATLAB port of the C port (without the whole-system functions), run in the MATLAB Function blocks of Simulink (`code="matlab"`). It follows the C port function by function and gives its results to the rounding errors, but uses the vector operations of MATLAB where the C port loops (e.g., the GradNets). A change in the C port must be mirrored here. Each C block of a netlist has its MATLAB code (`MCode` in `plecs/_netlist.py`, next to its C code in the control modules), from which `simulink/_mfunction.py` generates the MATLAB function of the block (the persistent state, the conversions of the signals, and the functions of the port that it uses as local functions) and the mask initialization collecting its parameters into the struct `p` (`[]` as NaN). The inputs without direct feedthrough come through unit delays, and the update with them is deferred to the next call. The MATLAB code must be valid for the code generation (fixed sizes and types, complex variables complex from their initialization). The lookup tables of the loci of the `ReferenceGenerator` are computed by the function `sm_reference_luts.m` (`PATH_FUNCTIONS` of `_mfunction.py`, written next to the model with both codes) in the mask initialization of Simulink (`Mask.simulink_init`), so that the block does not compute them at its start; in PLECS, the C-Script block computes them.
- `motulator_export/simulink/` writes Simulink models (`sm.py`, `im.py`, `grid.py`). The blocks of the classes are the C-Script code of the PLECS model wrapped in generated C MEX S-functions (`_sfunction.py`), or MATLAB Function blocks (`_mfunction.py`, `code="matlab"` of `write_model`), and the models are built in MATLAB by `build_drive.m` and `build_grid.m` with the common parts in the package `+blocks`. On Windows, the tests can use the MinGW-w64 gcc of MATLAB (on the PATH).
- Tests of the control systems: `tests/monolithic.py` defines each control system as one C-Script block running the whole-system functions of the C port, `tests/test_simulink.py` compares their S-functions with *motulator* in closed-loop simulations with a mock of the Simulink API (`tests/simulink_mock`), and `tests/test_control.py` executes the netlists with the S-functions of the blocks (`tests/netlist.py`, as Simulink does), with the parameters computed from the model initialization through the masks by an interpreter of the MATLAB subset (`tests/matlab.py`), compares them with *motulator*, checks that the results equal those of the monolithic control systems exactly, and checks the layouts for crossings. `tests/test_matlab_function.py` builds each control system with MATLAB Function blocks alone in Simulink (`tests/build_harness.m`), checks that the lines of the built model connect the ports of the netlist (`tests/model_lines.m`), and checks that it gives the outputs of the S-functions with the inputs of these closed-loop simulations.
- `examples/` contains the comparison scripts and the generated models (the Simulink build and initialization scripts and the S-function sources in `examples/simulink/`, and with `--matlab` the models `*_matlab.slx` with their MATLAB functions `mfun_*.m`). Regenerate the models by running the scripts after changing the writers, and check that the differences stay at the level recorded in `examples/README.md` and `motulator_export/simulink/README.md` (update the tables if they change). `examples/screenshots.py` remakes the screenshots of the README and their dark versions.

## Conventions

- Follow the conventions of *motulator*: peak-valued complex space vectors, SI units, NumPy-style docstrings, and line length 88.
- The package requires one minor release of *motulator* (e.g., `motulator>=0.15.1,<0.16` in `pyproject.toml`), since a new release may change its API; an update to a new release raises both bounds (and the version in the requirements of `README.md`).
- PLECS: the schematic coordinates are chosen so that wires do not cross and the labels are below the blocks (in the control systems, by the layout hints of the netlists). Only the signals fed back to the control system are measured with meters; the other signals use PLECS probes.
- Simulink: the blocks are aligned with the ports they connect to (`blocks.align`), so that the lines are straight, and the feedback lines are drawn through given corners (`blocks.route`).
