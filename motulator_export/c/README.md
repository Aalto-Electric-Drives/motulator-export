# C port

C port of the *motulator* control algorithms and models, run in the C-Script blocks of the PLECS models, in the S-functions of the Simulink models, and in the libraries of the native simulation (`motulator_export.native`).
The code follows the Python code of *motulator* closely, including the order of the state updates, and each header lists its Python counterparts.
Optional parameters (`None` in *motulator*) are represented by `NAN`, and their defaults are resolved in the C code, as in *motulator*.

Each class is a type with its functions (e.g., `FluxObserver` with `flux_observer_init`, `flux_observer_compute_output`, and `flux_observer_update`), which the blocks of the classes of the control systems run.
The measurements, the feedback signals, and the references between the blocks are signal vectors (meas, fbk, and ref), whose layouts are defined in the headers of the control methods (e.g., `MEAS_WIDTH` and `FBK_w_M` in `sm_flux_vector.h`) with their pack and unpack functions.
The whole-system functions (e.g., `vector_control_system_compute_output`) run the control system in one block; they are used by the reference control systems of the tests.
Their gate enable (`ControlSystem.set_enable` of *motulator*) selects the standby output of the controllers (e.g., `flux_vector_ctrl_compute_standby_output`) with the measured converter voltage, as in *motulator*; in the blocks of the classes, the block `compute_standby_output` of each controller selects the references.

## Native simulation

The libraries of the native simulation (`native_<name>.c`) combine the C port of a control system with C models of the system, which `sim.c` simulates as the simulation of *motulator* (`Simulation.simulate`): the control system is run at its sampling instants, the duty ratios pass through the computational delay and the PWM model, and the states are integrated between the sampling and switching instants by a port of the RK45 solver of scipy, taking the same steps.
A model (`Model` in `sim.h`) and a control system (`ControlSystem`) are interfaces of function pointers, embedded as the first members of the concrete types (e.g., `Drive` in `drive.h`).
The API functions setting the converter, its DC bus, and its modulator are in `sim.c`, those of the models in `drive.c` and `grid.c`, and those of the control systems in the libraries.
The states are complex and in the order of *motulator*, and the control system logs the signal groups of *motulator* (`ref` and `fbk`), described by a string of their fields (e.g., `FVC_FIELDS` in `native_sm.c`), so that the Python module fills the time series of the *motulator* objects and post-processes them as *motulator* does.
A new type of system needs its C model (e.g., a machine in `drive.c`), a library combining the model with the C port of its control system, and a Python module setting the parameters (e.g., `motulator_export/native/_im.py`).

The native simulation takes the same solver steps as *motulator*, so the results agree to the rounding errors: about 1e-12 relative to the signal magnitudes, also with the GradNet models, see `tests/test_native.py`.
With the carrier comparison (`pwm=True`), a rounding error can change a quantized duty ratio and thereby a switching instant, after which the solutions differ more; with a fine quantization (`CarrierComparison(N=2**24)`), they agree to about 1e-7.
Similarly, the diode bridge (`DiodeBridgeDCBus`) clamps its inductor current at zero, which makes the step sizes sensitive to the rounding errors (differences of about 1e-7 to 1e-5, depending on the system and the simulated time).
The closed-loop simulations of *motulator* itself are equally sensitive to the rounding errors.

## Tests

The tests in `tests/` compile the C sources with gcc and compare the results with *motulator* step by step, without PLECS.
They run in GitHub Actions on every push and weekly against the main branch of *motulator*, to detect changes in *motulator* that must be mirrored here.

## GradNets

Both *motulator* and the C port evaluate the GradNets in double precision, and the incremental inductances are computed from the analytic Jacobian of the flux map in both, so the tests compare the C port with *motulator* using the relative tolerance of 1e-9.
The sizes of the networks are limited by `GRADNET_MAX_IN_DIM` and `GRADNET_MAX_EMBED_DIM` in `gradnet.h`, which are checked both when a model is written and at the start of the simulation.

## Portability

The C port uses the C99 complex type (`complex.h`) in double precision, mirroring the complex space vectors of *motulator*.
It compiles with gcc, clang, MinGW-w64 (e.g., for `mex` in MATLAB), and the compiler bundled with PLECS, but not with MSVC, and embedded compilers may lack `complex.h`.
A conversion to a custom complex type or to single precision is straightforward with the C-port tests, but it is left until a concrete embedded target exists.
